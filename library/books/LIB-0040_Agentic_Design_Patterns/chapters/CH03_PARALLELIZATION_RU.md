# CH03 — Parallelization / Параллелизация

**Книга:** Antonio Gulli, *Agentic Design Patterns*. **Оригинал:** пользовательский PDF 48–63. Код автора (Marco Fago) на PDF 52–55: LangChain + `RunnableParallel` + финальный synthesis. **SOURCE_REVIEWED / CODE_CORRECTED / LAB_DESIGNED / NOT_RUN / NOT_QUALIFIED**.

## 1. Бизнес-задача

Пользователь задаёт тему. Система параллельно готовит:
- краткое объяснение;
- три вопроса;
- 5–10 ключевых терминов.

Дожидается всех результатов и составляет один общий ответ. Цель паттерна — **сокращение времени ожидания независимых I/O-вызовов**, а не создание дополнительных «разумов».

## 2. Процесс (BPMN 2.0 в текстовой форме)

`Start(topic) → Task(Validate input) → Parallel Gateway(split) → [Task(Summary) || Task(Questions) || Task(Key Terms)] → Parallel Gateway(join) → Task(Synthesis) → End(response)`.

Join ждёт **все три** независимые ветви. Если одна упала — нужен договорённый failure policy: в учебной версии FAIL с понятной ошибкой, в продакшне могут быть bounded retries, partial-result с маркировкой или ручной review.

## 3. Структура системы и информационные контракты

```text
User ── topic:string ──> Validate
                          │
                    parallel fan-out
          ┌───────────────┼─────────────────┐
          ▼               ▼                 ▼
      Summary          Questions         Key Terms
          │               │                 │
          └───────────────┼─────────────────┘
                          ▼
                  fan-in / join (dict)
                          │
                          ▼
                      Synthesis
                          │
                          ▼
                  Final response + trace
```

| Блок | Вход | Выход | Возможные ошибки |
|---|---|---|---|
| Input validator | `topic:str` | непустая строка | пустой/слишком большой ввод |
| `summarize_chain` | `topic` | `summary:str` | сетевой сбой / неверное содержание |
| `questions_chain` | `topic` | `questions:str` | неполный список вопросов |
| `terms_chain` | `topic` | `key_terms:str` | неверные/дублированные термины |
| `RunnableParallel` | `topic` | JSON-подобный `{summary, questions, key_terms, topic}` | любая ветвь упала |
| `synthesis` | вся структура | `answer:str` | неподтверждённый итог |

Из книги получаем **fan-out → fan-in → synthesis**. В FATHER дополнительно требуем `task_id`, `branch_id`, `source_refs`, `model_version`, `error_code`, `trace_id`. Генерация терминов из одной названной темы **не означает фактологической достоверности**.

## 4. Что исправлено относительно примера

1. Проверка `OPENAI_API_KEY` **до** инициализации модели/цепочек: оригинальный `llm=None` приводит к ошибке при сборке `prompt | llm`.
2. Минимальные зависимости `langchain-core` и `langchain-openai`; `langgraph` и `langchain-community` не требуются для этого конкретного примера.
3. `RunnableParallel` запускает независимые операции конкурентно; `synthesis` начинается **после** join.
4. `RunnablePassthrough()` с входом `str` действительно возвращает исходную тему; это не ошибка.
5. Используется `ainvoke` и ограничение `max_concurrency`; за реальные внешние rate limits отвечает дополнительно retry/backoff на стороне приложения.
6. `temperature=0.7` оставлена как авторский параметр; это не настройка достоверности. Допускается `temperature=0` для более стабильных опытов, но это не гарантия детерминизма.
7. Исключение одного из параллельных вызовов корректно обрабатывается на верхнем уровне. Синтез **не** вызывается с безымянной частичной выдачей.

## 5. Конкурентность vs вычислительный параллелизм

Async I/O позволяет ожидать сразу несколько HTTP-запросов без последовательной блокировки одного event loop. Это **не** значит, что три LLM одновременно вычисляются в одном потоке Python. Удалённые запросы обрабатывает инфраструктура провайдера; GIL не является прямым ограничением вычислений удалённой LLM. Для локальной CPU-bound обработки выбирать процессы/другие средства распараллеливания и оценивать contention GPU/VRAM.

Не гарантировать ускорение: rate limits, очереди модели, cold starts и медленная самая длинная ветвь могут свести выигрыш к нулю.

**Условная иллюстрация, не измерение:** последовательные три вызова по 2 секунды + синтез 2 секунды ≈ 8 секунд; конкурентные ветви по 2 секунды + синтез 2 секунды ≈ 4 секунды при отсутствии ограничений и накладных расходов.

## 6. Эволюция в FATHER

- **A — 1 Python-процесс:** `asyncio.gather()`, три mock-функции, один синтез.
- **B — один LLM SDK:** три `Runnable` + LCEL `RunnableParallel`; trace, valid input, договорённые таймауты.
- **C — несколько сервисов:** `task_id / correlation_id / branch_id`, брокер сообщений при обоснованной необходимости, Aggregator, дедупликация, deadline, DLQ, idempotency, UAG/ACL, внешняя проверка и POLYGON.

Инвариант: **синтезировать только результаты, связанные с одним task_id**; не объединять ответы из разных сессий или пользователей.

## 7. Что важно при переносе к ALINA

Если изучаем три первоисточника, каждый reader/extractor может работать независимо. Финальная **проверка доказательств и утверждений** обязана дождаться всех нужных результатов, иначе создаст неполный граф знаний. При отсутствии доказательств → `INSUFFICIENT_EVIDENCE`, а не выдуманная информация.
