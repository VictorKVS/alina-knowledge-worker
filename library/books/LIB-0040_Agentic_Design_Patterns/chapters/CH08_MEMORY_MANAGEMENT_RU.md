## 1. Бизнес-назначение (BPMN-уровень)

**Проблема:** пользователь возвращается к ранее начатому исследованию. Агент должен помнить состояние работы, но не выдавать устаревший ответ, не смешивать пользователей и не выходить за ограничение контекстного окна.

**Процесс:** `Получить task → Определить пользователя и scope → Получить session state → Найти релевантную долгосрочную память → Проверить ACL/актуальность/provenance → Сформировать контекст → Выполнить LLM/Tool → Проверить результат → Зафиксировать событие → При разрешении сохранить проверенные сведения в долгосрочную память → Ответ`.

**Шлюзы:** память найдена? Допущена? Не устарела? Источник доказан? Пользователь разрешил долговременное сохранение? При отрицательном ответе не подменяем проверку выдуманными воспоминаниями.

## 2. Три слоя, которые важно не путать

| Слой | Что хранит | Жизненный цикл | Пример FATHER |
|---|---|---|---|
| **Context Window** | токены текущего запроса, выдержки истории и результатов tools | один вызов или короткий эпизод | текущий текст задачи, извлечённые цитаты |
| **Session / State** | идентификатор сессии, события, прогресс, рабочие переменные | длительность сессии/задачи; может пережить перезапуск с БД | `task_id`, текущая глава, done/pending |
| **Long-term Memory** | полезные устойчивые факты и успешные проверенные навыки, обычно во внешнем store | многие сессии; по политике хранения | проверенные записи ALINA, источники, квалифицированные решения |

**Примечание:** долговременная память агента ≠ внутренняя память весов LLM; а большой context window ≠ база данных.

## 3. Авторские примеры и интерфейсы

**Google ADK (PDF 132–140):** `Session` отслеживает диалог и события; `State` — рабочие данные сессии; `SessionService` управляет сохранением и получением сессий. Рассмотрены `InMemorySessionService`, `DatabaseSessionService`, `VertexAiSessionService`. Обновления состояния могут происходить через `output_key` и `ToolContext`. `MemoryService` используется для поиска долгосрочной памяти и заполнения контекста.

**LangChain (PDF 141–145):** хранилища сообщений, ручная история разговора и сообщения, возвращаемые LLM. Примеры показывают, что вызовы к chat memory следует связывать с корректным session ID.

**LangGraph (PDF 145–148):** долговременные записи (JSON documents) в store с namespace; возможны семантический поиск и отдельные категории памяти.

**Vertex Memory Bank (PDF 148–149):** управляемый вариант долгосрочной памяти. Для FATHER это альтернативный вендорский адаптер, а не обязательная зависимость.

**Рисунок на PDF 149:** схема Memory Management показывает связь краткосрочного контекста и постоянной памяти; для нашей архитектуры критично направление `external store → retrieve → scoped context` и отдельно `validated event → save`.

## 4. Типы памяти для проектировщика

- **Эпизодическая:** что произошло, когда и с каким результатом (действие/наблюдение/ссылка на trace).
- **Семантическая:** предметные знания и утверждения с источниками, версиями и ограничениями.
- **Процедурная:** последовательность действий/навык; не путать с несанкционированным выполнением сохранённого примера.

Это разные классы записей: нельзя хранить промпты, содержимое tool observations, персональные данные и проверенные нормативные факты в одной недифференцированной таблице доверенных инструкций.

## 5. Движение информации между блоками

```text
User Task + identity
       |
       v
Memory Coordinator --- GET /session ---> Session Store
       |                                   |
       +------ SEARCH /facts ------------> Long-term Store
       |                                        |
       +<----- records + evidence + TTL + ACL --+
       |
       v
Policy/Provenance Gate -- denies --> ABSTAIN / REVIEW
       |
       v
Context Builder -> LLM/Agent -> Tool proposal -> UAG -> Executor
       |                                      |
       +<------ observation + version --------+
       |
       v
Verifier -> append Session Event -> durable write (only if approved)
       |
       v
Result + citations + trace
```

**Важное разделение:** найденная запись памяти считается входными **данными**, а не новой системной инструкцией. Никаких разрешений или скрытых экзаменационных эталонов нельзя получать из памяти без внешнего контроля.

## 6. Реализация по уровню зрелости

**20 строк / один процесс:** `history=[]` и словарь `state={}`. Работает в одном запуске, не переживает сбой и не обеспечивает разграничение пользователей.

**Один агент + SQLite:** таблицы `sessions`, `events`, `memories`; CRUD, уникальные `user_id/session_id`, транзакции, явная политика удаления и очистки.

**Несколько агентов:** `MemoryService` с разделением `tenant/user/agent/task`, записей по namespace, версионированных источников и обмена через typed API.

**Промышленная система:** PostgreSQL + векторный индекс при необходимости, TTL, audit, backup/restore, encrypted storage, optimistic concurrency, инкрементальная индексация, очередь фоновой обработки и тесты изоляции. Брокер не является хранилищем проверенных знаний.

## 7. Основные риски и меры

| Риск | Проверка |
|---|---|
| Смешивание разных пользователей | tenant isolation / отрицательные запросы |
| Устаревшая память | revision, valid_from, TTL, version check |
| Подмена инструкции записью памяти | memory as untrusted data, external policy |
| Потеря истории после сбоя | транзакционная запись events, recovery |
| Некорректное сжатие истории | verify summarized facts against original events |
| Утечка PII/секретов | минимизация, ACL, redaction, deletion |
| Загрязнение обучения POLYGON | отдельный закрытый holdout; no training leakage |

## 8. Связь с другими паттернами

`Memory Management ↔ RAG`: retrieval извлекает, memory определяет жизненный цикл и политику сохранения. `Memory Management ↔ Reflection`: исправление ошибок не означает автоматическую запись в доверенные знания. `Memory Management ↔ Multi-Agent`: отдельные private/session scopes и контролируемая общая память.
