## Тщательный разбор
### 1. Vocabulary bridge between GenAI and IT
Таблица 1.1 (PDF стр. 32) сопоставляет agent↔component, tool↔adapter, short-term memory↔session state, long-term memory↔system of record, multi-agent system↔component architecture. Это полезное сближение понятий, но не тождество поведения LLM и детерминированного компонента.

### 2. Abstractions and reusable design patterns
Автор предлагает рассматривать агентные паттерны как микоархитектуры из проверенных GoF и интеграционных паттернов. Оркестрация предполагает центральный управляющий компонент; хореография — взаимодействие по локальным правилам и событиям.

### 3. Orchestration versus choreography
Работа с LLM API рассматривается как взаимодействие с внешним сервисом с ограниченной предсказуемостью. Поэтому инженерные методы из области distributed systems применимы без изобретения всех механизмов заново.

## Инженерный алгоритм: наша адаптация для FATHER
1. Определить назначение каждого агента как компонента и границы его ответственности
2. Перечислить связи и контракты между компонентами
3. Определить, где нужна оркестрация, а где допустима хореография
4. Сопоставить уже известные паттерны с новой функцией и проверить отказоустойчивость

## Типовые ошибки и ограничения
- Не утверждать, что память агента всегда заменяет систему записи: требуются метаданные, версии, контроль доступа.
- Не выбирать message broker только из-за моды на multi-agent.
- Не считать LLM-выход проверенным фактом или допустимым действием.

## Применение в FATHER / ALINA / FRODO / POLYGON
FATHER устанавливает единый инженерный язык для ALINA, TIMA, FRODO и POLYGON; решения документируются ADR и component contracts.

## Углублённый инженерный разбор CH01

### 1.1. Словарь: почему переименование проблемы не решает её

По таблице 1.1 (PDF 32, печатная стр. 3) автор сопоставляет терминологию GenAI и традиционной разработки:

| GenAI | Инженерный аналог у автора | Граница аналогии |
|---|---|---|
| Agentic pattern | Microarchitecture из GoF/Fowler patterns | LLM внутри может нарушать контракт из-за недетерминированного текста |
| Agent | Component | Компонент обязан иметь наблюдаемые входы/выходы, а не только описанную роль |
| Short-term memory | Session state | Нужны id, lifetime, reset policy и правила хранения |
| Long-term memory | System of record | Ответ RAG не должен заменять авторитетный источник |
| Multi-agent system | Component architecture | Появляются распределённые ошибки, дубли действий и безопасность сообщений |
| Tool | Adapter | Инструмент выполняет действия только после проверки права и схемы |

Таблица — модель рассуждения автора, а не утверждение, что LLM полностью эквивалентна обычному сервису. Из неё для FATHER следует сформировать типизированный словарь архитектуры.

### 1.2. Пример перевода неопределённого требования в контракт

**Вход заказчика:** «Агенты автоматически исследуют документ и составят заключение».

Нельзя напрямую назначить `Agent A → Agent B → Agent C` и назвать это архитектурой. Требование нужно разложить на:
1. **Source Ingest Component**: принимает ссылку/файл, фиксирует SHA-256, origin, license, timestamp и scope.
2. **Knowledge Extractor**: возвращает структурированные фрагменты с `page, span, section, language`.
3. **Evidence Verifier**: проверяет связь утверждения с первоисточником. Статус `SUPPORTED / CONTRADICTED / UNKNOWN`.
4. **Decision/Report Component**: агрегирует только допустимые результаты; неизвестное выводит как неопределённость.
5. **Audit Store**: неизменяемая трасса запросов, разрешений, ответов и версий.

Это **наша декомпозиция FATHER**, не рисунок из книги. При этом каждый блок имеет независимо проверяемый контракт; LLM можно заменить без разрушения всей линии.

### 1.3. Orchestration и Choreography — два разных режима управления

Автор объясняет различие на PDF 35–36:
- **Orchestration:** центральный координатор определяет последовательность исполнения и наблюдает завершение.
- **Choreography:** участники реагируют на события без единого управляющего компонента.

**Где использовать в FATHER:** входной заказ, выделение прав, создание Blueprint и решение о приёмке требуют централизованной оркестрации. Фоновые независимые обновления индексов или уведомления о новых источниках могут использовать событийное взаимодействие. Не следует объединять эти модели в одну неконтролируемую петлю.

**Критический нюанс:** хореография не освобождает от общего policy enforcement. UAG должен обрабатывать вызовы инструментов независимо от формы сообщения.

### 1.4. Почему автор предпочитает микоархитектуру («microarchitecture»)

На PDF 33–37 автор связывает уровень agentic pattern с более общими программными паттернами и предлагает разбивать крупный шаблон на составные, давно известные решения. Это полезно для:
- оценки стоимости и пропускной способности отдельных стадий;
- изоляции отказов;
- независимой замены моделей и брокера;
- идентификации опасных побочных эффектов;
- повторного применения tested components.

Например, типичная петля ReAct может включать Strategy (выбор инструмента), Adapter (внешний API), Request–Reply (ответ инструмента), State Store (история), Retry с лимитом и внешний Authorization Gate. Этого набора недостаточно для production сам по себе — каждый контракт и ошибка требуют tests и evidence.

### 1.5. Сравнение «модный агентный фреймворк» и инженерного выбора

| Критерий | Framework-first | Pattern-first |
|---|---|---|
| Начальная точка | Выбранный SDK | Требования и архитектура |
| Межагентное взаимодействие | Встроенные абстракции SDK | Message/API contracts |
| Ошибки | То, что умеет фреймворк | Явная failure taxonomy |
| Замена модели | Зависит от SDK | Поставщик за Adapter |
| Квалификация | Демо работоспособности | Воспроизводимые тесты и независимая приёмка |

Это сравнительная таблица FATHER на основе направления главы, не экспериментальная оценка эффективности конкретных SDK.

### 1.6. Практический пример маршрута ALINA → FRODO → POLYGON

- ALINA анализирует главу о LLM-угрозах и записывает утверждение вместе с диапазоном источника.
- FRODO получает **учебный пакет** с видами угроз, защитными правилами и ожидаемой формой отчёта, но не закрытый holdout POLYGON.
- UAG не даёт учебному агенту реальные полномочия сканирования.
- POLYGON в будущем проверяет способности в песочнице, в том числе отказы, противоречия и объяснимость.
- Приёмка переводит только конкретные версии и согласованные компетенции в допущенный статус.

Этот сквозной пример показывает причину, по которой нельзя заменять архитектуру одним длинным системным промптом.

### 1.8. Признаки неготовой архитектуры

- Система отвечает, но не понятно, какой компонент получил право на действие.
- Два сообщения могут выполнить одну и ту же опасную операцию.
- Источник знаний невозможно проследить до версии и страницы.
- Сбой инструмента превращается в уверенный придуманный ответ LLM.
- Описание агента не содержит предела времени, денег, шагов и scope.
- Работающий POC выдаётся за квалифицированный продукт без регрессионного теста.

**Вывод для FATHER:** прежде всего проектировать системные границы и contracts, затем выбирать RabbitMQ, LLM, векторную БД и конкретный фреймворк. Именно в этом практическая ценность первого раздела книги.
