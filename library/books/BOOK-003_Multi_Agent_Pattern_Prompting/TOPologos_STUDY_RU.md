# Topologos — учебное пособие для первого курса МАИ

**Основа:** официальный GitHub Packt, [Topologos Manual v5](https://github.com/PacktPublishing/Building-Complex-Multi-Agent-Systems-Using-Pattern-Prompting/blob/main/Topologos-Manual.md) (разделы 1–21). Ниже — наша учебная интерпретация, а не копия оригинала.

## 1. Задача из жизни

Представь конструкторское бюро. Проект требует работу инженера-проектировщика, исполнителя, проверяющего и руководителя. Есть две проблемы:

1. **Порядок действий:** кто начинает, кому передаёт результат, кто принимает решение.
2. **Средство передачи:** как задание доходит до адресата, где хранится при его отсутствии и что происходит при отказе.

В терминах Topologos первое — **pattern layer**, второе — **topology layer**. Они проектируются раздельно.

## 2. Словарь

| Термин | Значение |
| --- | --- |
| Agent pattern | Повторяемая схема работы AI-агента: ReAct, RAG, Reflection, Planner и др. |
| Message broker | Сервер-посредник, который доставляет сообщения между сервисами |
| RabbitMQ | Конкретный брокер сообщений, использующий exchanges, queues, bindings |
| Exchange | Компонент RabbitMQ, маршрутизирующий опубликованные сообщения |
| Queue | Очередь ожидания для получения сообщений обработчиками |
| Routing key | Метка сообщения, применяемая exchange при маршрутизации |
| Consumer | Программа, получающая и обрабатывающая сообщение |
| ACK | Подтверждение успешной обработки сообщения |
| DLQ / Dead Letter Queue | Очередь для сообщений, не обработанных обычным способом |
| Retry / backoff | Повтор после ошибки с контролируемой задержкой |
| Idempotency | Защита от повторного побочного эффекта при повторной доставке |
| Vhost | Логический контур изоляции RabbitMQ |
| mTLS / OAuth2 | Механизмы установления доверия и авторизации |
| GoF | Классические объектно-ориентированные паттерны проектирования |
| EIP | Enterprise Integration Patterns — шаблоны интеграции систем |
| ADR | Запись архитектурного решения с причинами и альтернативами |

## 3. Два слоя и три действия

**Слой паттерна:** роли, обмен сообщениями, порядок, завершение.  
**Слой топологии:** exchanges, queues, правила доставки и отказов, доступы и эксплуатация.

На каждом слое:
- **Compose** — собрать существующие типовые блоки;
- **Extend** — дополнить готовый блок;
- **Define** — описать новый блок.

Например, базовый паттерн ReAct расширяем отдельной ролью проверки результатов, сохраняя инфраструктурные правила предприятия.

## 4. Алгоритм архитектора Topologos

**Фаза 1: Clarify.** Уточнить паттерн, нагрузку, инфраструктуру, требования безопасности, допуск к ошибкам. Руководство ограничивает интервью пятью вопросами. Недостающие параметры фиксировать как допущения, не выдавать за факты.

**Фаза 2: Pattern Analysis.** Рассмотреть пять «линз»: декомпозиция паттерна и топологии; GoF; EIP; модель угроз; анализ отказов.

**Фаза 3: Iterative Approval.** Предложить решение → объяснить через паттерны → указать плюсы и минусы → показать схему → получить явное Approve/Modify/Reject. Решения нельзя молча считать согласованными.

**Фаза 4: Final Output.** Выпустить семь артефактов: полная схема, манифест RabbitMQ, карта соответствия паттернов, security manifest, схема DLQ, эксплуатационные рекомендации, реестр активных определений.

## 6. Реальное применение к FATHER в 2026 году

Предлагаемый процесс:

```text
Заказчик → FATHER Controller
                  │
                  ▼
             ALINA / RAG
                  │
                  ▼
           System Architect
                  │
                  ▼
         UAG (права и допуск)
                  │
                  ▼
            TIMA / Worker
                  │
                  ▼
            POLYGON / QA
                  │
             PASS / RETRY
                  ▼
             Аудит / ADR
```

**Важно:** это проектное отображение принципов Topologos на нашу фабрику, а не точная схема из руководства.

В небольшом локальном MVP прямые вызовы Python-функций могут быть проще RabbitMQ. Брокер оправдан, если действительно нужны независимые очереди, асинхронные обработчики, восстановление после отказов, горизонтальное масштабирование и устойчивый обмен сообщениями.

## 7. Безопасность

Проверить, что исполнитель получает только разрешённые поля. Хранить чувствительные данные в специальном хранилище и передавать указатель (Claim Check), когда это оправдано. Установить изоляцию vhost, сервисные учётные записи, сроки хранения сообщений, шифрование, контроль прав, ограничения на replay.

Указанные в руководстве значения TLS, retry, TTL и оценки нагрузки следует проверять на применимость к реальному окружению. Нельзя объявлять статус «безопасно» по одному сформированному manifest.

## 8. Инженерные различия

| Неверное утверждение | Правильная инженерная позиция |
| --- | --- |
| «RabbitMQ гарантирует exactly-once» | Обычно проектируют at-least-once + idempotency и dedup |
| «LLM нарисовала схему, значит рабочая архитектура готова» | Нужны schema validation, интеграционные, failure и security тесты |
| «Повторим все ошибки три раза» | Классифицировать ошибки; постоянные ошибки и poison messages обрабатывать иначе |
| «Любая LLM должна запускать код» | Tool access должен контролироваться за пределами сгенерированного текста |
| «Всем системам нужны очереди» | У очередей есть стоимость и операционная сложность |

## 9. Проверка

Задание: в FATHER агент получает запрос, вызывает инструмент, инструмент не отвечает 10 секунд. Нарисуй три исхода: успешный повтор, исчерпание retry, эскалация человеку. Укажи `correlation_id`, `action_id`, `retry_count`, кто разрешает исполнение и чем доказывается отсутствие повторного опасного действия.
