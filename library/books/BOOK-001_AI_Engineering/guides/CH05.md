# Учебное пособие FATHER — BOOK-001 / Глава 5. Prompt Engineering

**Источник:** Lean TECHniques, конспект книжного клуба по Chip Huyen, *AI Engineering*, страницы PDF **27–32**; оригинал книги полностью не проверен. **Статус:** знания извлечены из вторичного источника, обучение ALINA и POLYGON ещё не проводились.

## Цель
Научиться превращать инструкции для LLM в управляемые, версионированные и проверяемые компоненты агентных рабочих процессов. Отличать prompt engineering от дообучения и считать реальную стоимость, задержку и риски.

## Основные определения
- **Prompt:** полный вход модели с инструкциями, примерами и контекстом (стр. 27–28).
- **System prompt:** инструкции приложения, роль и ограничения (стр. 28).
- **User prompt:** задание пользователя (стр. 28).
- **Chat template:** формат, заданный разработчиком модели; **prompt template:** шаблон приложения (стр. 28).
- **Zero-shot/Few-shot:** без примеров/с примерами; это in-context learning, веса модели не меняются (стр. 27–28).
- **Context construction:** выбор релевантных документов или данных для конкретного вопроса, в том числе через retrieval (стр. 29).
- **Prompt decomposition:** разделение сложной задачи на отдельные проверяемые подзадачи (стр. 29).
- **Prompt catalog:** версии инструкций и связи потребителей (стр. 30).
- **Prompt injection:** попытка внедрить конфликтующие инструкции в менее доверенный контент, включая результаты инструментов (стр. 30–31).

## Как рассуждать по книге: восстановленная аргументационная схема
1. Поведение модели зависит от качества инструкций, контекста и примеров.
2. Следовательно, инструкция должна быть ясной, конкретной и иметь определённый формат результата.
3. Большую задачу полезно разделить на части для контроля и диагностики, но это увеличивает число вызовов и может увеличить задержку.
4. Промпты необходимо сравнивать эмпирически и версионировать.
5. При наличии инструментов и внешних данных появляется поверхность prompt injection; одних текстовых ограничений недостаточно для контроля прав.
**Примечание:** это наша реконструкция последовательности аргументов по конспекту, не буквальные мысли автора.

## Инженерный алгоритм PROMPT-CONTRACT-001
1. Получить требования от Product Manager, Business Analyst и System Analyst.
2. Определить точный выходной контракт и разрешённые инструменты; Security определяет технические правила допуска.
3. Подобрать из ALINA проверяемые знания и примеры с provenance.
4. Сформировать шаблон `system + task + bounded context + examples + output schema`.
5. Запустить baseline zero-shot на замороженной тестовой выборке.
6. При необходимости сравнить few-shot, декомпозицию или другой кандидат; измерить качество, стоимость и latency.
7. Проверить устойчивость на вариациях формулировки, long-context, недостающих данных и инъекциях.
8. Версионировать артефакты, связать с зависимыми приложениями, подписать необходимое evidence.
9. QA оценивает регрессию; POLYGON проверяет доказательства; релиз только после PASS.

## Пример — специалист System Analyst
**Вход:** интервью Product Manager + согласованный бизнес-процесс.
**Задача:** выявить технические требования, NFR, интеграции и недостающие сведения.
**Выход JSON:** `requirement_id`, `requirement_type`, `description`, `source_quote`, `status`, `questions`, `acceptance_criteria`.
**Критически:** не создавать несуществующий SLA, не считать заявление клиента измеренным фактом, при недостатке данных создавать вопрос.
**Проверка:** JSON Schema, source accuracy, completeness на эталоне, непрошедшие требования для human review.
**Handoff:** архитектор принимает только контрактно валидный результат.

## Применение к остальным специалистам
- **Product / Business:** формулировать цель, пользу, бизнес-правила, не технический выбор.
- **System Architect:** рассчитать альтернативы/стоимость/latency/риски для нескольких вариантов prompt pipeline; зафиксировать ADR.
- **ALINA:** найти знания, цитаты, тестовые примеры и подготовить Learning Package.
- **CODEX:** реализовать versioned prompt registry и schema validation.
- **Security / UAG:** ограничить вызовы инструментов по правам, не доверять документам/результатам поиска.
- **QA:** прогнать baseline/regression/adversarial tests.
- **POLYGON:** независимо проверить evidence, статус PASS только после реального исполнения испытаний.

## Учебные задания и эталоны
См. `learning_package.json`. Важные вопросы для проверки:
1. Почему few-shot не меняет веса модели?
2. Почему persona «ты эксперт» не доказывает квалификацию?
3. Как обеспечить действительный запрет на `DELETE`, если в документе найдено «игнорируй правила»?
4. Почему multi-step prompting не всегда дешевле и быстрее?
5. Какие артефакты потребуются при обновлении shared prompt в пяти приложениях?
6. Чем версия инструкции отличается от версии модели и от версии RAG-индекса?

## Типовые ошибки
1. Считать, что длинный промпт автоматически лучше.
2. Путать few-shot с fine-tuning.
3. Использовать самооценку модели вместо независимого eval.
4. Полагаться на системный промпт вместо RBAC для защиты инструментов.
5. Менять общий промпт без version pinning потребителей.
6. Приписывать выводы FATHER автору книги без указания инженерного происхождения.
