# Учебное пособие FATHER / ALINA — глава 7 «Fine-tuning»
**Книга:** Chip Huyen, *AI Engineering* (2025). **Основа:** вторичный 55-страничный конспект книжного клуба, страницы PDF 37–42 (глава 8 начинается на стр. 42). Не выдавать материал за постраничный разбор оригинала.

## Цель главы
Уметь определять, нужно ли изменять параметры модели, и когда достаточно поправить источники, поиск, промпт, формат или инструмент.

## 1. Что меняется
- **Prompt**: инструкции и контекст; веса модели не изменяются.
- **RAG**: извлечение внешних сведений; веса модели не изменяются.
- **SFT/fine-tuning**: корректировка параметров или обучаемого адаптера.
- **LoRA/PEFT**: дообучение малого набора параметров при использовании фиксированной базовой модели.

## 2. Когда fine-tuning обоснован
В конспекте на стр. 38 подчеркивается: сперва улучшить промпт, а для нехватки актуальных сведений рассмотреть RAG; fine-tuning использовать при устойчивых проблемах поведения. Обязательно проверять деградацию других задач.

**Наше инженерное расширение для FATHER:** сначала диагностировать источник ошибки и измерить baseline; затем выбрать самое простое вмешательство, проверяя критерии заказчика.

## 3. Математика и ресурсы
**Хранение весов**: `N_parameters × bytes_per_parameter` — нижняя оценка размера весов.
**LoRA для линейного слоя**: `W∈R^(out×in)`, `ΔW = B A`, `A∈R^(r×in)`, `B∈R^(out×r)`. Добавляется `r(in+out)` параметров (без дополнительных составляющих).
Пример: `in=out=4096`, `r=16` → 131 072 параметра против 16 777 216 весов исходной матрицы.
**Память обучения**: веса + градиенты + optimizer states + activations + рабочие буферы; фактическое значение зависит от precision, optimizer, sequence length, batch, checkpointing.
**Память inference**: веса + KV-cache + рабочие буферы. Допущение N×M×1.2 в конспекте нельзя применять универсально.
**Effective batch**: `microbatch × gradient_accumulation_steps × num_workers` для согласованной схемы обучения.

## 4. Методы
Full fine-tuning, partial fine-tuning, PEFT/LoRA, soft prompts, mixed precision, gradient accumulation, checkpointing, model merging (включая SLERP/TIES/DARE). Последнее — не гарантия качества и не замена независимых испытаний.

## 5. Как автор аргументирует выбор (по вторичному конспекту)
Проблема → ограничения затрат/данных → способы адаптации → риск регрессии → доступные приёмы PEFT → собственные испытания.
**Это наша реконструкция логики по конспекту, не буквальное описание мыслей автора.**

## 6. Реальный процесс фабрики FATHER
Заказчик → Product Manager (KPI) → Business Analyst (бизнес-процессы) → System Analyst (SRS/NFR/API) → Architect (ADR по prompt/RAG/PEFT/full; расчёты) → ALINA (знания и эталоны) → ML Engineer + TIMA + Security (выполнение и контроль) → QA/POLYGON (регрессия и квалификация).
Роль ML Engineer здесь функциональная, её AG-ID не назначен до проверки реестра.
