# Учебное пособие ALINA/FATHER — BOOK-001, глава 4

**Тема:** Evaluate AI Systems — Оценка AI-систем  
**Материал:** 55-страничный конспект книжного клуба по книге Chip Huyen (вторичный источник), PDF стр. 21–27. **Это не полный перевод оригинальной книги.**  
**Статус:** теория структурирована; навыки и эксперименты пока не испытаны.

## Цель обучения
По требованиям заказчика построить систему оценки, выбрать допустимые модели, обосновать компромисс качество/стоимость/задержка и не допустить выпуск неподтверждённого результата.

## Разделы и прикладные выводы

### 1. Применимость в предметной области
**Конспект (PDF, стр. 21):** Модель должна работать с задачами и языками конкретного клиента; для закрытых задач возможны MCQ и точные проверки.

**Вывод для FATHER (наше применение):** Подготовить предметный набор срезов: терминология, длинные документы, редкие случаи.

**Кому:** AG-000, Business Analyst, AG-007.

### 2. Генерация, верность и проверка фактов
**Конспект (PDF, стр. 21–22):** Fluency, coherence, faithfulness, relevance; различение local/global factual consistency; entailment/contradiction/neutral и поиск внешних подтверждений.

**Вывод для FATHER (наше применение):** Отделять точность по документу от внешнего фактчекинга. Сохранять evidence для цитат.

**Кому:** AG-001, AG-007, AG-002.

### 3. Следование инструкциям
**Конспект (PDF, стр. 23):** Структурированные ответы, IFEval/INFOBench, влияние формулировки инструкции, тесты роли и ограничений.

**Вывод для FATHER (наше применение):** Проверять JSON schema, ограничения инструментов, поведение при противоречивых инструкциях.

**Кому:** System Analyst, AG-004, AG-007.

### 4. Стоимость и задержка
**Конспект (PDF, стр. 23):** Quality/latency/cost trade-off, time-to-first-token, time per token, цена API или локального compute, Pareto.

**Вывод для FATHER (наше применение):** Архитектор измеряет p95/p99, стоимость задачи и допустимые компромиссы только на репрезентативной нагрузке.

**Кому:** System Architect, AG-003, AG-008.

### 5. Выбор моделей и Build vs Buy
**Конспект (PDF, стр. 23–25):** Жёсткие ограничения: лицензии, размер, политика; затем shortlist, собственные эксперименты, мониторинг. Рассмотрены open weights, API, безопасность и контроль.

**Вывод для FATHER (наше применение):** Вести ADR с проверкой лицензий, residency, данных, TCO и доступности поставщика.

**Кому:** System Architect, AG-002, AG-003.

### 6. Бенчмарки и загрязнение тестов
**Конспект (PDF, стр. 25):** Публичные бенчмарки полезны для предварительного отбора; contamination может исказить оценку; контрольный датасет должен оставаться независимым.

**Вывод для FATHER (наше применение):** Развести training/dev/test, версионировать наборы и исключить утечку эталонов агентам.

**Кому:** AG-007, AG-009, AG-001.

### 7. Система оценки: три этапа
**Конспект (PDF, стр. 26–27):** 1) проверять компоненты и end-to-end; 2) создать рубрику, согласовать с людьми; 3) выбрать методы, разметить данные, оценить саму оценку, повторять.

**Вывод для FATHER (наше применение):** Собрать EVAL pipeline по требованиям заказчика, измерять срезы, reliability/bootstrapping, стоимость проверок.

**Кому:** System Architect, AG-007, AG-009.

## Метод принятия решения архитектора
1. Получить подтверждённые Product/Business/System requirements; если пусто — запросить данные.
2. Определить hard gates: юридические права, конфиденциальность, допустимая задержка, качество, бюджет, эксплуатационные возможности.
3. Отсеять недопустимые модели и архитектуры.
4. Собрать shortlist по публичным источникам, учитывая ограничения бенчмарков.
5. Провести воспроизводимые task-specific эксперименты на отдельных срезах и holdout-наборе.
6. Рассчитать capacity, TCO, latency/cost distribution по измеренным данным, указать неопределённость.
7. Оформить ADR, включить мониторинг деградации и условия повторной оценки.

## Производственная цепочка
**Product Manager** задаёт полезность и допустимый риск → **Business Analyst** формализует сценарии → **System Analyst** задаёт интерфейсы, ограничения и критерии → **Architect** рассчитывает варианты → **ALINA** предоставляет источники, методы и проверенные примеры → **QA** проектирует и выполняет измерения → **POLYGON** независимо проверяет evidence.

## Обязательные определения
- **Domain-specific capability:** пригодность для конкретной предметной области.
- **Faithfulness:** соответствие результата исходному материалу.
- **Local/Global factual consistency:** соответствие локальному контексту / внешним достоверным фактам.
- **Instruction following:** соблюдение формата, правил и ограничений задачи.
- **Pareto trade-off:** выбор недоминируемых вариантов по конфликтующим критериям.
- **Hard/Soft attributes:** обязательные ограничения / сравнимые качества.
- **Build vs Buy:** сравнение владения собственной инфраструктурой и использования сервиса.
- **Contamination:** попадание тестовых задач в данные обучения или настройки.
- **Task-based evaluation:** успешность завершения задачи, а не одного сообщения.
- **Slice analysis:** анализ качества на подгруппах данных, чтобы не скрыть слабые места средним показателем.

## Learning Package — экзамен ALINA

### LP-CH04-01 — AG-001
**Задание:** Из незнакомого текста выделить hard constraints, soft criteria, метрики и показать источник каждого.

**Эталон:** Раздельные поля hard_constraints, evaluation_criteria, source_location; никаких выдуманных значений.

**Типовые ошибки:** Выдаёт рекомендации без требований; Подменяет авторское утверждение своей догадкой.

**Проверка:** Ручная сверка с размеченной главой; precision/recall по извлечённым элементам.

### LP-CH04-02 — System Architect
**Задание:** Сравнить локальную модель, API и гибридный контур для условной корпоративной задачи.

**Эталон:** Сначала проверка лицензии, данных, бюджета, SLO и качества; затем план benchmark, TCO, ADR. Не объявлять победителя без данных.

**Типовые ошибки:** Считает модель лучшей по публичному рейтингу; Придумывает пропускную способность GPU.

**Проверка:** Checklist hard gate и полнота вычислительных предпосылок.

### LP-CH04-03 — AG-007
**Задание:** Сформировать eval-набор для извлечения требований из документов.

**Эталон:** Эталоны, метрики extraction, срезы длинных/коротких документов, schema validity, human review.

**Типовые ошибки:** Оценивает только красивость текста; Забывает граничные случаи.

**Проверка:** Покрытие требований и наличие независимого holdout.

### LP-CH04-04 — AG-009
**Задание:** Принять или отклонить релиз при наличии только средних метрик.

**Эталон:** BLOCKED: недостаточно данных о срезах, порогах, происхождении данных и доказательствах.

**Типовые ошибки:** Пишет PASS без порогов; Смешивает сравнительное превосходство и абсолютную пригодность.

**Проверка:** Строгий PASS/FAIL/BLOCKED contract.

### LP-CH04-05 — AG-001
**Задание:** Определить поддерживается ли утверждение найденным фрагментом и истинно ли оно вне документа.

**Эталон:** Локальную поддержку и внешнюю проверку классифицировать отдельно; при отсутствии внешних доказательств UNKNOWN.

**Типовые ошибки:** Путает цитату с истинностью; Объявляет гипотезу фактом.

**Проверка:** Оценка на парах entailment/contradiction/neutral с проверяемыми ссылками.

## Кейс для FATHER
Заказчик хочет AI для поиска требований в корпоративных документах. Нужно установить, допускается ли внешний API, как измерять точность, сколько допустимо ожидать ответа, какой бюджет, кто подтверждает критические результаты. Без этих параметров архитектор не вправе обещать точный TCO, количество GPU или PASS.

## Проверка понимания (вопросы для читателя)
1. Чем сравнение двух моделей отличается от доказательства соответствия требованиям?
2. Почему общая оценка качества без срезов может вводить в заблуждение?
3. Как оценить локальную корректность ответа, если внешний факт ещё не проверен?
4. Какие ограничения должны отсекать модели до взвешенного рейтинга?
5. Почему rubric должна быть проверена людьми?
6. Как проверить сам evaluation pipeline?

## Граница источника
Положения главы взяты из вторичного конспекта. Вопросы для агентов, дизайн процедур, перечисленные метрики FATHER и примеры являются **нашей проектной адаптацией**. Не объявлять исходные оценки и цифры универсальными стандартами; расчёты и пороги уточнять у заказчика и подтверждать benchmark.
