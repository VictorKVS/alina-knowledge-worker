# BOOK-002 / CH03 — Vocabulary and Tokenization

**Источник:** Suhas Pai, *Designing Large Language Model Applications*, оригинал PDF, стр. 168–203. Это самостоятельный русскоязычный учебный материал для первокурсника МАИ; не копия книги.

## 1. Зачем это знать

LLM принимает не «слова в человеческом понимании», а последовательность **token IDs**. Токен может быть символом, частью слова, словом или служебным маркером. У конкретной модели свой словарь. Поэтому одно и то же письмо, фрагмент программы или технический стандарт у двух моделей занимает разное число токенов.

**Для FATHER:** ALINA должна учитывать конкретный tokenizer revision перед расчётом окон контекста, созданием промптов, разбиением RAG-корпуса и подбором модели для русского языка.

## 2. Словарь модели

PDF 168–177: автор показывает токены GPT-NeoX, символ пробела `Ġ`, регистр, числа и части слов; вводит OOV и компромисс по размеру словаря. Чем больше словарь, тем меньше может быть токенов на текст, но редкие элементы хуже обучаются; оптимум зависит от модели и вычислений.

**Один токен не обязан быть одним словом**. Точное число токенов нельзя оценивать исключительно по числу символов.

## 3. Токенизатор и четыре стадии

Согласно PDF 178–190:
1. **Normalization:** регистр, Unicode, диакритика; менять смысл нельзя без проверки.
2. **Pre-tokenization:** первичное деление текста и пунктуации, обычно с offset.
3. **Tokenization:** BPE, byte-BPE, WordPiece, Unigram LM (последний назван, но не разобран подробно).
4. **Postprocessing:** модельные специальные маркеры.

На практике не всякий токенизатор использует все четыре стадии одинаковым образом.

## 4. BPE — алгоритм на примере книги

Исходные слова из PDF 191–192: `bat, cat, cap, sap, map, fan`. В начале словарь содержит буквы. Считаем соседние пары: `ap=3`, `at=2`, `ca=2`. Объединяем самую частую пару `a+p → ap`. Повторяем подсчёт и слияние до выбранного размера словаря. При инференсе применяем **сохранённые правила слияния в том же порядке**, а не обучаем BPE заново на вопросе пользователя.

Псевдокод:

```text
vocab = unique_base_symbols(corpus)
sequences = split_into_symbols(corpus)
while len(vocab) < target_size:
    pair = argmax(count_adjacent_pairs(sequences))
    if pair_count(pair) == 0: break
    merged = concatenate(pair.left, pair.right)
    sequences = merge_every_occurrence(sequences, pair)
    vocab.add(merged)
    rules.append(pair)
```

Это упрощённая схема для обучения, не реализация byte-level BPE промышленной модели.

## 5. WordPiece

В PDF 194–195 автор сравнивает WordPiece с BPE. Для пар применяется нормализация частот:

`score(a,b) = freq(a,b) / (freq(a) * freq(b))`.

Далее на этапе применения WordPiece используется поиск наиболее длинного подходящего субслова из словаря. Алгоритм и реализация могут различаться между библиотеками: сравнительный критерий здесь — изложение книги.

## 6. Byte-level BPE

PDF 193–194: токенизация на базе байтов позволяет кодировать любые Unicode-символы через их байтовые последовательности, предотвращая OOV в этой модели представления. Это особенно важно для смешанных русско-английских текстов, символов и технических документов. Byte-level BPE **не означает**, что каждое кириллическое слово занимает один токен.

## 7. Специальные токены

PDF 196–199: `PAD`, `EOS`, `UNK`, маркеры инструментов и их результатов. Конкретные строки и идентификаторы служебных токенов зависят от модели. В агентных системах **служебный токен не должен самостоятельно предоставлять права инструмента**; их проверяет UAG.

## 8. Метрики fertility и parity

PDF 200–201:

`Fertility = tokens_in_corpus / words_in_corpus`. При 250 токенах на 100 слов: `F=2.5` (меньше — компактнее, но компактность сама по себе не равна качеству ответа).

`Parity_RU/EN = tokens_ru / tokens_en` на **семантически эквивалентном тексте**. Пример 180 / 100 = 1.8. Это не «80% хуже» по качеству, а разница в стоимости представления.

## 9. Добавление специальных терминов в словарь

PDF 201–202: автор добавляет специализированные токены к FLAN-T5 и вызывает `resize_token_embeddings`. Важно: **новые embeddings ещё не обучены**. Их необходимо обучать (например, при дальнейшей адаптации модели). Менять словарь у рабочей модели без совместного контроля версии токенизатора, весов и индексов нельзя.
