## Ключевой тезис

Для production-quality LLM системы нужны программные компоненты, оркестрация, ограничения и экономическая оптимизация, не одна монолитная модель (683–684). Критерии: качество, стоимость, latency и надёжность.

## Архитектурные паттерны

### Multi-LLM

Разные задачи требуют разных способностей: выбирать минимально достаточную LLM на конкретный компонент. Второй вариант: группа моделей умеет одну задачу, но выбирается одна или подмножество. Возможен ансамбль; это не значит, что большинство обязательно право.

### Cascades

На запрос сначала отвечает малая модель, при недостаточной уверенности — средняя, затем большая. Выгода максимальна, когда большинство запросов решает малая. Проблема: самоотчёт LLM об уверенности ненадёжен (предупреждение автора на странице 688). Использовать внешние тесты/калибровку, а не единственное `confidence: 0.99` модели.

### Routers

Перед исполнением маршрутизатор выбирает подходящую модель; в отличие от каскада, не обязан запускать одну задачу на нескольких моделях. Ошибка роутера сама становится ошибкой всего продукта. Применимо к выбору RAG retriever.

### Task-specialized LLM

Сложная задача декомпозируется, подзадачи идут специализированным исполнителям. Для FATHER идея расширяется до версионированной компетенции: агент получает только разрешённые знания, инструменты и квалификацию POLYGON.

### DSPy

DSPy отделяет программный flow от итерируемых переменных. **Modules** описывают этапы приложения через **signatures** (например `document -> summary`); **optimizers** настраивают инструкции, few-shot примеры и параметры модели с помощью заданной метрики. Автор предупреждает, что автоматическая оптимизация не всегда эффективна и нередко требует ручной работы.

### LMQL

Декларативный язык для ограничений вывода и управления потоком генерации через программную структуру. Полезно сравнить с простым Python + JSON Schema; внедрение по доказанным результатам.

## Практическая интерпретация для FATHER

**Это архитектурная адаптация проекта FATHER, не прямая схема автора:**

`customer requirements → ALINA evidence KB → Block Matcher → competent Model/Tool Router → Agent Factory → UAG → verifiers → POLYGON → admission`.

Для FRODO использовать безопасный специализированный контур проверки LLM/агентов, а не отдавать недоверенному генератору произвольные полномочия.

## Проверки

- Полезен ли каскад по сравнению с фиксированной малой/большой моделью?
- Когда роутер выбирает неверный ресурс?
- Сохраняется ли качество при смене модели?
- Может ли DSPy улучшить точность, а не только усреднённую метрику на учебном наборе?
- Чем ограниченное структурное выполнение отличается от self-reported confidence?
