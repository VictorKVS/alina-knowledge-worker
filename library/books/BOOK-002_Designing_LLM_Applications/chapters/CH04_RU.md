## 1. После токенизации: векторы и веса

`text → token IDs → embedding lookup → hidden states → transformer layers → logits → probabilities`.

Token ID — **индекс**, не численная семантика. Embedding lookup возвращает обучаемый вектор. При предобучении веса первоначально инициализируются, а не содержат заранее готовое понимание мира (208).

Модель получает сигнал из последовательностей и обучается, уменьшая loss. Принцип: gradient descent обновляет параметры в направлении уменьшения ошибки. Меньше train loss **не** равно «лучший OSINT-аналитик»: нужны отдельные прикладные тесты.

## 2. Self-attention и математика

Входной массив X проектируется в Q, K и V:

`Q=XW_Q; K=XW_K; V=XW_V`.

`A = softmax(Q K^T / sqrt(d_k) + mask)`

`Y=A V`

Маска определяет, какие токены могут видеть друг друга. У decoder-only причинная маска препятствует обращению к **будущим** токенам при генерации. Multi-head attention — набор параллельных проекций, а не отдельные программные агенты.

### Учебный расчёт

Пусть один query `q=[1,0]`, два keys `k1=[1,0]`, `k2=[0,1]`. Скалярные оценки: `[1,0]`. После деления на sqrt(2) и softmax веса примерно `[0.670,0.330]`. При `v1=[2,0]` и `v2=[0,2]` получается `[1.340,0.660]`. Числа — учебные, не результат измерения реальной LLM.

## 3. Позиции, FFN, нормализация

- **Positional encoding:** информация о порядке; книга сравнивает абсолютные позиции, ALiBi, RoPE, NoPE (221–223).
- **FFN:** отдельное нелинейное преобразование вектора каждого токена, обычно с расширением скрытого пространства (223–224).
- **LayerNorm:** числовая нормировка с обучаемыми scale/shift для устойчивости (224–226).

Важно: детали расположения нормализации и использования RoPE зависят от модели; схема — учебное обобщение, не универсальный blueprint.

## 4. От предсказания к обучению

Для правильного токена y с вероятностью p(y) при one-hot метке cross-entropy:

`L = -ln p(y)`.

Если p=0.1, L≈2.303; если p=0.8, L≈0.223. После forward pass считается loss, затем градиенты backprop и шаг оптимизатора.

В оригинале (228) perplexity записана как `2^CrossEntropy`; это соответствует энтропии в **битах**. При natural-log cross-entropy используется `exp(L)`. Нельзя смешивать основания логарифмов.

**Intrinsic** — качество вероятностного моделирования текста; **extrinsic** — реальная целевая задача. Для ALINA важны оба, но выпуск агента определяется также последним, безопасностью и регрессией.

## 5. Архитектуры

- **Encoder-only:** представления, классификация, часть embedding/retrieval моделей (229–232).
- **Encoder-decoder:** преобразование последовательности в последовательность, например T5 (233).
- **Decoder-only:** автогрегрессионное продолжение, семейство GPT (233–234).

Не делать архитектурный выбор только по популярности: сначала оценить реальную задачу, качество, аппаратные ресурсы, условия лицензии и работу с русским языком.

## 6. Mixture of Experts

MoE включает gating/router для выбора небольшого числа внутренних нейросетевых экспертов (234–238). Это **не** наш Agent Factory и не отдельные OSINT/кодовые программные агенты. Возможны проблемы распределения нагрузки.

## 7. Цели обучения

| Objective | Что предсказываем | Поддержка в книге |
|---|---|---|
| FLM | Следующий токен, причинная модель | 240–247 |
| PrefixLM | Суффикс после видимого двунаправленного префикса | 247–248 |
| MLM | Скрытые токены/интервалы входа | 248–253 |
| UL2 mixture | Набор режимов denoising | 253–255 |

Обучение на MLM не означает автоматически лучшую прикладную классификацию: нужен эксперимент. Обозначить target loss, маску доступности контекста и контрольный downstream тест.

## 8. Главный предметный кейс: шахматы

В PDF 255–262 автор описывает обучение LLM на Lichess PGN: источники шахматных партий, собственная нотация ходов, словарь и next-token objective. Затем описывает сравнение с естественно-языковыми фразами о ходах; в его эксперименте модель с PGN показывает лучшие результаты, чем модель на текстовых описаниях.

**Вывод автора:** специализированные языки/нотации могут передавать предметные концепции эффективнее естественного языка. Это **не универсальная теорема** о любом агенте.

Вместо того чтобы хранить всё лишь в неструктурированном prompt, можно обучать агента явным контрактам:

```json
{
  "event": "DOCUMENT_VERSION_FOUND",
  "source_id": "S-012",
  "previous_version_id": "S-010",
  "decision": "NEW_VERSION",
  "evidence_span": "document section 7",
  "review_required": true
}
```

Для проверки полезности таких контрактов надо сравнить одни и те же задачи: свободный текст vs структурированное событие, измерить точность, стоимость, false merges, robustness и переносимость на другие агенты.

## 9. Значение для FATHER

**ALINA:** выбирает Knowledge, Prompt, RAG, Learning и Qualification Packages с учётом возможностей модели.

**FATHER Architect:** выбирает архитектуру по задаче, а не по моде.

**Agent Factory:** собирает workflow и tool contracts; MoE не подменяет обычную агентную архитектуру.

**POLYGON:** проверяет не только loss, но и качество реальных решений.
