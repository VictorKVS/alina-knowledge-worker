# Глава 1 — Introduction: как устроена и применяется языковая модель

**BOOK-002 / CH01.** Основа: Suhas Pai, *Designing Large Language Model Applications* (2025), оригинал PDF **стр. 27–91**. Это самостоятельное русскоязычное объяснение, не перевод главы.

## 1. Зачем это нужно

Заказчик просит: «Хочу задавать вопросы по документам организации». Новичок отвечает: «Скачаем LLM и подключим PDF». Инженер сначала выясняет, **почему нужен именно такой инструмент, какая информация допустима к обработке, как отличить правильный ответ и сколько будет стоить эксплуатация**.

Глава начинает с устройства языковой модели и постепенно приводит к примеру `Chat with your PDF` — разговорному поиску по документу. Это удобная последовательность: **понять механизм → научиться вызывать → собрать прототип → увидеть его ограничения**.

## 2. Языковая модель — простая аналогия

Представь студента, который тысячи раз решал задание «продолжи фразу». После большого количества тренировок он лучше предсказывает, какие слова естественно следуют за предыдущими. Модель обучается похожим образом, только использует числовые представления слов или их частей и большие матрицы параметров.

### Термины без сложных формулировок

| Термин | Объяснение | Где встречается |
| --- | --- | --- |
| LLM | Большая математическая модель, работающая с последовательностями токенов | Чат, извлечение фактов, генерация |
| Token | Фрагмент текста, единица словаря токенизатора; **не обязан** совпадать со словом | Подсчёт контекста и оплаты |
| Parameter / вес | Число, которое модель изменяет в ходе обучения | Размер модели, качество, память |
| Context | Текст и иные данные, которые доступны модели в текущем запросе | Системная инструкция, история, документы |
| Prompt | Инструкция или запрос, который подаётся модели | Классификация, объяснение |
| Zero-shot | Запрос без демонстрационных примеров | «Определи тональность» |
| Few-shot | Запрос с несколькими примерами | «Вот три классификации; сделай четвёртую» |
| Hallucination | Убедительно выглядящая, но неподтверждённая информация | Придуманные факты, неверные ссылки |
| API | Программный интерфейс вызова модели из другого приложения | Backend на Python |
| Embedding | Числовое представление текста для сравнения смысла | Поиск |
| Chunk | Небольшая порция извлечённого документа | Индексирование PDF |

**Важно:** модель предсказывает распределение вероятностей следующего токена, а не подбирает единственное «правильное» слово. См. PDF стр. 29–31.

## 3. Что модель делает при генерации

Упрощённо:
1. Токенизатор преобразует входную последовательность в токены.
2. Нейросеть по своим весам вычисляет оценки возможных следующих токенов.
3. Правило декодирования выбирает продолжение.
4. Новый токен добавляется к текущему контексту.
5. Процесс повторяется, пока не выполнено условие завершения.

Пояснение через условные числа: если для фразы «Сегодня идёт ...» система оценила варианты «дождь»: 0,70, «снег»: 0,25, «поезд»: 0,05, эти числа показывают **модельную оценку следующего токена в условном примере**, а не объективную вероятность погоды.

### Почему «правдоподобно» не значит «истинно»

Предсказание текстового продолжения само по себе не гарантирует проверку законов физики, содержимого базы, последнего приказа или точного вычисления. Поэтому для надёжной системы нужны **внешние данные, инструменты и независимая проверка**.

## 4. Виды взаимодействия с моделью

**Zero-shot:** прямо формулируем задачу и допустимые ответы.  
**Few-shot:** показываем несколько примеров ввода/вывода; веса модели от этого **не изменяются**.  
**Prompt chaining:** последовательно выполняем отдельные более узкие операции и передаём результат дальше.  
**Adversarial prompting:** проверяем, может ли вредоносный текст нарушить ограничения приложения.  
**API:** серверное приложение вызывает модель по формальному интерфейсу и обрабатывает результат.

Автор отдельно предупреждает о **prompt drift**: при смене модели или сервиса ранее удачная инструкция может работать хуже. Следовательно, мы версионируем инструкции и сравниваем их на постоянном тестовом наборе (см. PDF стр. 59–61).

## 5. Пример книги — «Chat with your PDF»

В PDF стр. 78–86 описывается прототип, в котором:
1. Пользователь загружает PDF.
2. Программа разбирает документ и выделяет текстовые фрагменты.
3. Фрагменты преобразуются в embeddings.
4. Векторные представления сохраняются для поиска.
5. Запрос пользователя тоже преобразуется в вектор.
6. По близости выбираются наиболее релевантные фрагменты.
7. Они передаются модели как контекст.
8. Модель формирует ответ для интерфейса.
9. История диалога участвует в последующих обращениях.

**Наше важное инженерное расширение:** использовать ссылки на исходные страницы, ACL, разделение клиентов и контроль данных до передачи во внешние модели.

## 6. Математика первокурсника

Для двух числовых векторов `a=(1,0)` и `b=(0.8,0.6)` косинусное сходство:

`cos(a,b) = (a·b) / (||a||·||b||) = 0.8 / (1·1) = 0.8`.

Вектор `c=(0,1)` имеет с `a` сходство 0. Это учебная геометрическая иллюстрация. **В реальной embedding-модели** смысловая близость связана с тем, как модель обучена формировать векторы; геометрическая близость не равна достоверности факта.

## 7. Почему прототип недостаточен для промышленной эксплуатации

В PDF стр. 86–90 автор обсуждает переход к production. В нашей архитектурной интерпретации пробелы прототипа проверяются по следующим направлениям:

- качество поиска и ответа: что делать, когда источник не найден?
- обработка данных: чтение PDF, таблиц, страниц с иллюстрациями;
- границы доступа: можно ли показать чужой документ?
- размещение: где обрабатываются текст, embeddings, логи и результаты?
- наблюдаемость: можем ли объяснить, почему был дан неверный ответ?
- стоимость и задержка: какой профиль нагрузки, какие SLO?
- воспроизводимость: какая версия модели, промпта, индекса и кода?

## 8. Как применить это в 2026 году

Первый практический уровень: локальный поиск по разрешённым документам без LLM. Второй: embeddings и поиск с измерением Recall@k. Третий: генеративная модель, проверяемые цитаты и безопасный контекст. Четвёртый: нагрузочные тесты, UAG, monitoring и журналирование.

Технологии-кандидаты: Python/FastAPI, SQLite FTS5 на начальном этапе, FAISS/Qdrant/pgvector для векторного retrieval, llama.cpp или разрешённый модельный API — после проверки локальной доступности, лицензий, контекста и стоимости.

## 9. Маленькое практическое задание

Задача: у тебя пять документов. Пользователь спрашивает «Как зависит память модели от длины контекста?». Ученик должен:

1. Найти документ, в котором описан KV-cache.
2. Показать идентификатор источника.
3. Объяснить, почему ответ нельзя строить из случайного первого результата.
4. Сказать «не найдено», если подходящих сведений нет.
5. Повторить эксперимент на заранее подготовленных вопросах.

**Эталонный ответ:** программное решение получает проверяемый документ или явно сообщает о недостатке информации; ссылки ведут к действительным фрагментам. Фактический уровень выполнения должен подтверждаться тестами.

## 10. Вопросы самопроверки

**Чем few-shot отличается от fine-tuning?** Few-shot предоставляет примеры в контексте без изменения параметров; fine-tuning обновляет обучаемые параметры модели.

**Почему embedding-поиск не гарантирует истинность?** Он возвращает близкие по определённой метрике представления; фактологическая достоверность требует отдельной проверки.

**Что такое успешный прототип?** Демонстрация основной функции. Это ещё не доказательство надёжности, безопасности и выполнения SLO.

**Что является опасной ошибкой?** Поместить конфиденциальный PDF во внешний сервис без предварительной проверки прав, условий обработки и архитектурных ограничений.
