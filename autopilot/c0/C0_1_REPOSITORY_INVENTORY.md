## Confirmed existing architecture

`KNOWLEDGE_CORE` already defines the production chain:

`SOURCE → SNAPSHOT → CHUNK → CLAIM → EVIDENCE → REQUIREMENT / CONTROL / METHOD → EXPERIMENT → RESULT → VERIFIED_PATTERN → SKILL → AGENT_VERSION → WORKFLOW → RUN → OUTCOME`

It also defines canonical stores for Source Registry, immutable originals, normalized corpus, Claim/Evidence, Knowledge Graph, vector index, patterns, experiments/evals, skills, agents/models, workflows and audit.

Therefore new ALINA K3→K10 work MUST reuse or extend these contracts unless a measured incompatibility is demonstrated.

## Vertical mapping

### ALINA Legal & Compliance / «Алина Правовед»
Canonical foundation: `KNOWLEDGE_CORE/security-knowledge`.

Observed capabilities already specified:
- immutable/versioned normative sources;
- structural legal address;
- atomic `SEC-REQ-*` candidates;
- obligation/prohibition/permission/condition/exception/responsibility types;
- subject/object/action/conditions/exceptions/deadlines/evidence;
- applicability;
- role-specific flows;
- controls/checks/evidence;
- continuous update/diff/impact model.

Decision: DO NOT create a parallel Legal DB during C0.

### ALINA Project / Organization & Competency
Canonical foundation: `KNOWLEDGE_CORE/docs/FATHER_ROLE_KNOWLEDGE_SYSTEM.md` plus Competency Lab.

Existing role model includes:
`ROLE → REQUIRES COMPETENCY → READS KNOWLEDGE DOMAIN → USES METHOD/TOOL → PRODUCES ARTIFACT → HANDS OFF → PASSES GATE → RECEIVES OUTCOME → EARNS VERIFIED EXPERIENCE`.

Decision: ALINA Project becomes an analytical/orchestration projection over the Role Knowledge System, not a second profession registry.

### ALINA Self / Agent Engineering
Canonical foundation: Knowledge Acquisition & Agent Factory plan + Role Knowledge System, applied with `role = ALINA`.

Decision: ALINA Self is self-application of the same specialist/agent factory. It may add ALINA-specific competencies, methods, prompts, RAG profiles, evals and gaps without forking the canonical knowledge model.

## Shared canonical chain

`Document → Requirement → Obligation → Role → Competency → Knowledge → Method → Agent → Action → Control → Evidence`

This is a cross-domain integration view, not permission to collapse distinct legal, knowledge, role and runtime entities into one table.

## Anti-duplication decisions

1. No new independent ALINA Legal database before C0 schema comparison.
2. No new independent ALINA profession/competency database before mapping Role Knowledge System.
3. No second Knowledge Graph solely for ALINA; ALINA needs a role/project projection over the canonical graph.
4. Existing ALINA SQLite/FTS5 remains an ingestion/runtime cache until migration/adaptation is justified.
5. `KNOWLEDGE_MASTER` is not deleted or declared obsolete yet; its useful contracts must be compared with `KNOWLEDGE_CORE`.
6. OSINT remains evidence supplier; Analyst/Verifier decides promotion.
7. Competency Lab supplies measurable training/evaluation evidence.
8. Automation Control Center supplies orchestration telemetry and must not become a source of domain truth.
